PavingOS Engineering Specs

Eng Spec 1 - Gemini

This is a detailed engineering specification for PavingOS.

As a Senior Staff Engineer, my primary focus here is reliability in the field (offline first), data integrity (financials), and scalability of the logic (estimating calculations).

The architecture deviates from a standard CRUD app to accommodate the "Day 1 Requirement" of offline support for Foremen. We cannot rely on simple browser caching; we require a local database synchronized with the server.

1. Architecture Overview

We will utilize a Hybrid Architecture:

Office App (Owner/Ops/Estimator): A standard server-rendered Next.js application optimized for desktop/tablet. Focus is on complex forms and data visualization.

Field App (Foreman): A Local-First PWA (Progressive Web App) running on Next.js, utilizing a client-side database (SQLite via WASM) that syncs to Supabase.

High-Level Stack

Frontend: Next.js 15 (App Router).

Hosting/Edge: Vercel.

Database: Supabase (PostgreSQL).

Offline Sync Engine: PowerSync (Recommended). It connects Supabase Postgres to a client-side SQLite database, allowing the Foreman to work 100% offline and sync when connectivity returns.

Background Jobs: Inngest (via Vercel Integration) for QuickBooks syncing and async calculations.

System Diagram Description

Client (Field): Writes to local SQLite. PowerSync SDK uploads mutations to Supabase.

Client (Office): Reads/Writes directly via Next.js Server Actions (or Supabase SDK) for real-time connectivity.

Supabase:

Postgres: Core data storage.

Auth: Handles JWTs and Row Level Security (RLS).

Realtime: Pushes updates to Office dashboards.

Integration Layer (Inngest):

Listens for job.status = 'completed' events.

Triggers transformation of Job Data → QBO Invoice.

Handles QBO OAuth token refreshing and retry logic.

2. Data Model

The schema must support the "Snapshot" pattern. When an Estimate becomes a Job, data must be copied, not referenced, so that changing a template price today does not alter the historical margin analysis of a job done last month.

3. API & Edge Functions

We will prioritize Server Actions for the Office App and Sync Protocol for the Field App.

Critical Server Actions (Office)

createEstimateFromTemplate(templateId): Deep clones a template into a new estimate.

convertEstimateToJob(estimateId):

Creates jobs row.

Deep copies estimate_line_items to job_budget (to track variance).

Sets status to scheduled.

syncToQuickBooks(jobId): Manually triggers the Inngest workflow.

Field App Sync Strategy (The Offline Challenge)

The Foreman app must not fail when the network is flaky (common on paving sites).

Read: The Foreman's device downloads a "Bucket" of data (Assigned Jobs + associated Line Items) via PowerSync to local SQLite.

Write: Foreman writes to local SQLite.

Sync: When network is available, the sync engine pushes mutations to the Supabase write-API.

Conflict Resolution: Last-write-wins is acceptable for this MVP, as Foremen rarely edit the same job simultaneously.

Inngest Background Functions

jobs/completed:

Trigger: jobs table update where status changes to completed.

Action: Generate Invoice JSON -> Authenticate QBO -> Post Invoice -> Save QBO Invoice ID to jobs table.

pricing/update-rates:

Scheduled: Weekly.

Action: Analyze job_actuals vs estimates to suggest new production rates to the Owner (Feedback Loop).

4. Auth & Security Considerations

Row Level Security (RLS)

This is a multi-tenant application. Strict RLS is required on every table.

Policy: auth.uid() IN (SELECT user_id FROM organization_users WHERE org_id = current_row.org_id)

Role-Based Access Control (RBAC)

We will implement RBAC logic within RLS policies or middleware.

Foreman:

READ: Only jobs assigned to them OR jobs scheduled for "Today".

WRITE: Only job_actuals and job_status. Cannot see pricing or margins.

Owner/Estimator: Full Access.

QuickBooks OAuth

Tokens must be encrypted at rest in the organizations table or a dedicated integrations table.

We must handle the "Refresh Token" rotation gracefully. If a token expires during a sync, the Inngest job must pause, alert the user to re-authenticate, and retry.

Field Device Security

Foremen devices are often shared. We should implement a "Session Pin" (4 digits) that wraps the long-lived Auth token, preventing accidental data entry by the wrong crew member if the phone is passed around.

Scenario A (Office): Create Estimate -> Convert to Job.

Engineering Specification — PavingOS (Next.js + Vercel + Supabase)

1) Architecture overview

Goals

Fast, opinionated estimating workflow + tight feedback loop from actuals → templates.

“Foreman-first” mobile UX with minimum viable offline: view job, start/complete, notes, photos, sync later.

High-level

Frontend + API: Next.js (App Router) deployed on Vercel.

Auth/DB/Storage/Realtime: Supabase (Postgres + RLS + Storage).

Integrations: QuickBooks Online via Intuit OAuth2 + QBO APIs.

Offline: Service Worker + IndexedDB queue for “job events” + photo staging; background sync when online.

Runtime split

Vercel Edge: lightweight auth/session handling, reads, caching, web middleware.

Vercel Serverless: QBO OAuth callbacks, invoice creation, sync jobs (need Node libs).

Supabase Edge Functions (Deno): optional for webhook ingestion + lightweight DB writes (can keep everything in Vercel if preferred; pick one and standardize).

Core flows

Estimating

Templates (assemblies) → estimate → approval.

Inline “historical actuals” surfaces from past jobs linked to the template/assembly.

Estimate → Job

Approved estimate converts to a job (no re-entry).

Field execution (offline-capable)

Foreman actions append immutable job_events (started/completed/notes/photos/labor hours).

Client writes to IndexedDB first; syncs when online; server applies idempotently.

Job costing feedback

Job aggregates actuals from events into job_actuals_summary.

Variances update template insights (never auto-mutate template rates without explicit user action).

Invoice → QuickBooks

Completed job generates invoice draft; ops reviews; push to QBO; store QBO IDs + sync state.

2) Data model (Supabase Postgres)

Multi-tenant first-class: everything scoped to org_id. Use RLS everywhere.

3) API / Edge Functions

Use Next.js Route Handlers (/app/api/...) as the primary API. Keep it boring.

Core API

POST /api/estimates create draft from template

POST /api/estimates/:id/approve → converts to job (transaction)

POST /api/jobs/:id/events append job event (idempotent via client_event_id)

POST /api/invoices/:id/push-to-qbo creates/updates QBO invoice, persists qbo_invoice_id

Offline sync contract (critical)

Client stores events in IndexedDB.

On reconnect: batch send job_events[] to POST /api/jobs/:id/events/batch

Server:

validates membership + role

inserts only new client_event_ids

triggers recompute of summaries/variances (DB function or background job)

QuickBooks Online

GET /api/qbo/connect start OAuth (redirect to Intuit)

GET /api/qbo/callback exchange code → store tokens in qbo_connections

POST /api/qbo/webhook (optional)

verify signature, enqueue sync work, update qbo_sync_state

POST /api/qbo/sync/customers (admin/ops)

POST /api/qbo/sync/accounts-items (admin/ops)

Token refresh

Prefer a scheduled job (Vercel Cron) that refreshes tokens nearing expiry and updates qbo_connections.

Never refresh from the client.

4) Auth + security considerations

Auth

Supabase Auth (email + magic link to start; add SSO later if needed).

Session on server using @supabase/ssr (Supabase recommends this over deprecated auth helpers).

Authorization

RLS policies on every table:

user must be in org_memberships for org_id

role gates:

foreman: read job, create job_events, upload photos

ops/owner: everything + invoicing + QBO sync

estimator: templates/estimates, read variances

Enforce org_id from server-side session; never trust client-provided org_id.

Data integrity

Use DB constraints:

unique idempotency key: (org_id, client_event_id)

foreign keys everywhere

Convert estimate → job via a transaction:

lock estimate row

verify approved

create job + snapshot fields

mark estimate “approved”

Storage security

Photos bucket private.

Upload via server-minted signed upload URLs.

Serve via signed read URLs with short TTL.

Supply-chain + runtime security (don’t ignore this)

Keep React patched: there have been critical RSC vulns recently; stay current and pin exact versions in lockfile.

Enable Dependabot + npm provenance checks where possible.

Strict CSP + secure headers in Next.js.

Rate limit sensitive endpoints (/api/qbo/*, auth, event ingest) using middleware.

PII

Minimal: names, emails, jobsite addresses, photos.

Encrypt QBO tokens at rest (Supabase Vault or app-layer encryption + KMS).

3. Offline Strategy (Authoritative)

Philosophy

This is not a full local-first replica.

This is minimum viable offline, optimized for reliability and speed.

Client Behavior

Foreman actions are written first to IndexedDB.

Each action generates a job_event with a UUID client_event_id.

Photos are staged locally until upload succeeds.

Sync runs automatically when connectivity is detected.

Server Behavior

Events are appended idempotently.

Duplicate client_event_ids are ignored.

Derived summaries are recomputed server-side.

Why This Approach

Predictable

Auditable

Easy to reason about

Avoids premature sync-engine complexity
